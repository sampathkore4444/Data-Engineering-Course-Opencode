## Apache Flight SQL notes. 

## Apache Arrow Flight SQL — Notes

**Apache Arrow Flight SQL** is a protocol for accessing SQL databases and analytical engines over **Apache Arrow Flight**, instead of traditional JDBC/ODBC-style row-by-row data transfer.

Think of it as:

> **SQL + high-performance Arrow columnar data transfer + gRPC**

### 1. Where Flight SQL fits

```text
                    Application
                         |
                    SQL Query
                         |
                         ▼
              ┌──────────────────┐
              │  Flight SQL      │
              │     Client       │
              └────────┬─────────┘
                       │
                  Arrow Flight
                    / gRPC
                       │
                       ▼
              ┌──────────────────┐
              │  Flight SQL     │
              │     Server      │
              └────────┬─────────┘
                       │
                       ▼
              ┌──────────────────┐
              │ SQL Engine / DB  │
              │                  │
              │ DuckDB           │
              │ Data Warehouse   │
              │ Database         │
              │ Query Engine     │
              └──────────────────┘
```

The important point:

**Flight SQL does not replace the database/query engine.**

It provides a standardized way for a client to **send SQL and receive the result efficiently**.

---

# 2. Traditional JDBC vs Flight SQL

Suppose we execute:

```sql
SELECT branch_id, SUM(amount)
FROM transactions
GROUP BY branch_id;
```

### JDBC approach

```text
Database
   |
   | rows
   ▼
JDBC Driver
   |
   | Java objects
   ▼
Application
```

Large result sets can involve significant object creation and serialization.

### Flight SQL

```text
Database / Query Engine
          |
          | Arrow RecordBatches
          ▼
     Flight Server
          |
       gRPC/HTTP2
          |
          ▼
     Flight Client
          |
          ▼
    Arrow Table
```

The result can remain in **Arrow's columnar representation**.

That is one of the major benefits.

---

# 3. Why Apache Arrow matters

Traditional relational result:

```text
Row 1 → [101, "Phnom Penh", 500]
Row 2 → [102, "Siem Reap", 700]
Row 3 → [103, "Battambang", 300]
```

Arrow stores data column-wise:

```text
branch_id:
[101, 102, 103]

branch_name:
["Phnom Penh", "Siem Reap", "Battambang"]

amount:
[500, 700, 300]
```

This is very efficient for analytics.

---

# 4. Flight SQL vs Apache Arrow

They are related but different.

### Apache Arrow

Defines the **in-memory columnar data format**.

```text
Arrow Table
   ↓
Columnar memory
```

### Apache Arrow Flight

Defines a **high-performance transport protocol** for Arrow data.

```text
Arrow data
   ↓
Flight
   ↓
Network
```

### Flight SQL

Adds **SQL/database semantics** on top of Flight.

```text
SQL
 ↓
Flight SQL
 ↓
Arrow Flight
 ↓
Arrow
```

So you can remember:

```text
              Flight SQL
                  │
             SQL protocol
                  │
            Arrow Flight
                  │
          gRPC / transport
                  │
              Apache Arrow
                  │
        Columnar memory format
```

# 6. Important Flight SQL concepts

You will frequently see these concepts:

### `ExecuteStatement`

Used to execute SQL.

```sql
SELECT *
FROM transactions;
```

Conceptually:

```text
Client
  |
  | ExecuteStatement(SQL)
  ▼
Server
```

---

### `GetFlightInfo`

The server provides information about how/where the result can be retrieved.

Think:

```text
"Here is the information required to fetch your query result."
```

---

### `DoGet`

Actually retrieves the result data.

```text
Flight Server
      |
      | DoGet
      ▼
Arrow RecordBatches
      |
      ▼
Flight Client
```

---

### `DoPut`

Used when the client needs to send Arrow data to the server.

For example:

```text
Python
  |
  | Arrow Table
  ▼
Flight SQL Server
  |
  ▼
Database / Processing Engine
```

# 7. RecordBatch is important

Flight generally doesn't have to send one enormous Arrow table.

It can stream:

```text
RecordBatch 1
      ↓
RecordBatch 2
      ↓
RecordBatch 3
      ↓
RecordBatch 4
      ↓
...
```

For example:

```text
10 million rows

        ↓

Batch 1 → 100,000 rows
Batch 2 → 100,000 rows
Batch 3 → 100,000 rows
...
Batch 100
```

This is useful for large analytical queries because the client can process data **as it arrives**.

Imagine a bank has:

```text

```

stored in Parquet:

```text

                       |

                       ▼
                Flight SQL Client
                       |
                       | Flight / gRPC
                       ▼
                Flight SQL Server
                       |
                       ▼
                    DuckDB
                       |
                       ▼
                Parquet files
```

The query engine reads Parquet, performs the aggregation, and returns the result as Arrow data.

# 10. Flight SQL vs REST API

A normal REST API might return:

```json
[
  {"branch_id": 101, "amount": 500},
  {"branch_id": 102, "amount": 700}
]
```

For millions of rows, JSON can be expensive.

Flight SQL:

```text
SQL query
   ↓
Arrow columnar result
   ↓
Binary transport
```

Much better suited for **large analytical datasets**.

## So, Can’t we use Apache Arrow on Oracle database?

Yes — **you can use Apache Arrow with Oracle Database**, but there is an important distinction:

> **Arrow is not a replacement for Oracle's database protocol.** It is mainly a data representation/transport layer that can sit around Oracle.

### Typical Oracle → Arrow architecture

```text
                Oracle Database
                       │
                 SQL / Oracle Driver
                       │
                       ▼
              Python / Java / C++
                       │
                 Convert result
                       │
                       ▼
                 Apache Arrow
                       │
            ┌──────────┼──────────┐
            ▼          ▼          ▼
         Pandas      Polars      ML
```

For example, with Python you can query Oracle and convert the result into a PyArrow table:

```python
import oracledb
import pyarrow as pa

conn = oracledb.connect(
    user="bank",
    password="password",
    dsn="oracle-host:1521/ORCL"
)

cursor = conn.cursor()

cursor.execute("""
    SELECT branch_id, amount, transaction_date
    FROM transactions
    WHERE transaction_date >= DATE '2026-03-01'
""")

rows = cursor.fetchall()

table = pa.Table.from_pylist(
    [
        {
            "branch_id": r[0],
            "amount": r[1],
            "transaction_date": r[2]
        }
        for r in rows
    ]
)
```

Now:

```text
Oracle
   │
   │ Oracle protocol
   ▼
oracledb
   │
   │ conversion
   ▼
Apache Arrow Table
   │
   ├──► Pandas
   ├──► Polars
   ├──► DuckDB
   └──► ML
```

### But what about Flight SQL?

This is the important difference.

You **cannot simply enable Arrow Flight SQL on Oracle** and expect Oracle to speak Flight SQL.

You would normally need an intermediate Flight SQL server:

```text
                     Oracle
                       │
                       │ SQL
                       ▼
                Flight SQL Server
                       │
                Arrow Flight
                       │
                       ▼
                Flight SQL Client
                       │
                       ▼
               Arrow / Polars / ML
```

The Flight SQL server could query Oracle using an Oracle driver and expose the results through Flight SQL.

### Why would you do this?

Imagine your bank has:

```text
Oracle Core Banking
       │
       │ 500M transactions
       ▼
Flight SQL Gateway
       │
       │ Arrow
       ▼
Analytics / Data Science
```

Instead of every analytics application having to understand Oracle-specific connectivity, they can use a **common SQL + Arrow interface**.

So:

**Oracle → query engine/database**

**Arrow → efficient data representation**

**Flight SQL → standardized SQL access + Arrow-based transport**

And this is especially interesting if you have **Oracle + DuckDB + Parquet + Python/Polars** in the same analytics architecture.


## So, basically Apache Flight is for parquet file query or like that?

Not exactly. **Apache Flight is not specifically for Parquet.**

The easiest way to remember it is:

> **Parquet = storage**
> **Arrow = in-memory data**
> **Flight = network transport**
> **Flight SQL = SQL interface over Flight**

### Example with Parquet

Suppose you have:

```text
/data/transactions/
    2026-01.parquet
    2026-02.parquet

```

DuckDB queries them:



So **Flight doesn't query the Parquet file itself**.

The **query engine** does that.

you can have:

### And Flight SQL adds SQL

Plain Flight:

```text

  │
  │ "Give me this Arrow dataset"
  ▼

```

Flight SQL:

```text
Client
  │
  │ SELECT ...
  ▼
Flight SQL Server
  │
  ▼

  │
  ▼
Arrow result
  │
  ▼

```

So **Flight SQL is not a Parquet technology either**.

It can sit in front of many data sources:

```text
                 Flight SQL
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Oracle     DuckDB      PostgreSQL
                    │
                    ▼

```

### One sentence to remember

**Parquet stores the data → DuckDB/Oracle queries the data → Arrow represents the result → Flight transports the result → Flight SQL lets you submit SQL to the server.**


## Is this a Flight SQL?

SELECT branch_id, SUM(amount)
FROM read_parquet('/data/transactions/*.parquet')
GROUP BY branch_id;

No. **That SQL query itself is not Flight SQL.**

It is **DuckDB SQL** that uses DuckDB's `read_parquet()` function.

```sql
SELECT branch_id, SUM(amount)
FROM read_parquet('/data/transactions/*.parquet')
GROUP BY branch_id;
```

The architecture is:

```text
              SQL Query
                  │
                  ▼
              DuckDB
                  │
          read_parquet()
                  │
                  ▼
             Parquet files
                  │
                  ▼
             Query result
                  │
                  ▼
             Arrow data
```

### Where Flight SQL comes in

If you expose that DuckDB through a Flight SQL server:

```text
Client
  │
  │ Flight SQL request
  │
  │ SELECT branch_id, SUM(amount)
  │ FROM ...
  ▼
Flight SQL Server
  │
  ▼
DuckDB
  │
  ▼
Parquet
  │
  ▼
Arrow RecordBatches
  │
  │ Apache Flight
  ▼
Client
```

So there are **two different things**:

| Component        | What it does                                         |
| ---------------- | ---------------------------------------------------- |
| `read_parquet()` | DuckDB reads Parquet                                 |
| SQL query        | DuckDB executes the query                            |
| Apache Arrow     | Represents result in columnar format                 |
| Apache Flight    | Transports Arrow data over network                   |
| **Flight SQL**   | Provides a SQL API/protocol for accessing the server |

### Very important distinction

This:

```sql
SELECT ...
FROM read_parquet(...)
```

is **DuckDB SQL**.

Whereas:

```text
Client → Flight SQL → Server → DuckDB → Parquet
```

is an **architecture using Flight SQL**.

So **Flight SQL doesn't mean "SQL for Parquet."** It means **"a standardized way to execute SQL remotely and retrieve the results efficiently using Arrow Flight."**

```text

  = STORE

  = QUERY

  = REPRESENT
```

For a bank's centralized analytics platform, that second architecture is where it starts becoming interesting.


## So, client writes a duckdb query?

**Yes — in this particular architecture, the client can write a DuckDB SQL query.** But there is an important distinction.

### Your example

Client sends:

```sql
SELECT
    branch_id,
    SUM(amount) AS total_amount
FROM read_parquet('/data/transactions/**/*.parquet')
WHERE transaction_date >= '2026-03-01'
GROUP BY branch_id;
```

The Flight SQL server passes that SQL to **DuckDB**.

```text
Client
   │
   │ SQL
   │
   ▼
Flight SQL Server
   │
   │ DuckDB SQL
   ▼
DuckDB
   │
   ▼
Parquet
```

### But there is a problem

If the client writes:

```sql
FROM read_parquet('/data/transactions/**/*.parquet')
```

the client needs to know the **server's filesystem/path**.

That's usually undesirable.

Instead, the server could expose a logical table/view:

```sql
SELECT
    branch_id,
    SUM(amount)
FROM transactions
GROUP BY branch_id;
```

And internally:

```text
Flight SQL Server
       │
       ▼
DuckDB
       │
       ▼
transactions view
       │
       ▼
Parquet files
```

For example, DuckDB could define:

```sql
CREATE VIEW transactions AS
SELECT *
FROM read_parquet('/data/transactions/**/*.parquet');
```

Then the client only needs to know:

```sql
SELECT
    branch_id,
    SUM(amount) AS total_amount
FROM transactions
GROUP BY branch_id;
```

### So the better architecture is

```text
              CLIENT
                 │
                 │ Standard SQL
                 ▼
          Flight SQL Server
                 │
                 ▼
              DuckDB
                 │
          ┌──────┴──────┐
          │             │
       Views        Tables
          │
          ▼
       Parquet
```

**Important:** Flight SQL does not require the SQL to be DuckDB-specific. Ideally, the Flight SQL server exposes a standard SQL interface and hides the underlying storage/engine details.

So your client thinks:

> "I'm querying a `transactions` table."

It doesn't need to know:

> "There are 500 Parquet files sitting under `/data/transactions/` and DuckDB is reading them."


## Do we need to install Flight SQL server separately?

Yes — **if you want a client to connect remotely using Flight SQL, you need a Flight SQL server component running somewhere.**

But **Flight SQL is not one single server product** that you install like MySQL.

### In your DuckDB + Parquet example

You would have:

```text
                 Client
           Python / Java / BI
                  │
                  │ Flight SQL
                  ▼
        ┌───────────────────┐
        │ Flight SQL Server │  ← separate service
        │                   │
        │      DuckDB       │
        └─────────┬─────────┘
                  │
                  ▼
              Parquet
```

The Flight SQL server acts as the **network/API layer** in front of DuckDB.

### Without Flight SQL

If everything is on the same machine:

```text
Python
  │
  ▼
DuckDB
  │
  ▼
Parquet
```

You don't need Flight SQL.

### With Flight SQL

If multiple applications need to remotely query your data:

```text
Python ───────┐
              │
Java ─────────┤
              │
BI Tool ──────┤
              ▼
       Flight SQL Server
              │
              ▼
           DuckDB
              │
              ▼
           Parquet
```

Then you need a Flight SQL server implementation.

### One important clarification

You don't necessarily install **"Apache Flight SQL Server"** as a standalone Apache product.

Flight SQL is a **protocol/specification**. You need a server implementation that supports it.

For example, a data platform might implement:

```text
Flight SQL Server
       +
    DuckDB
       +
   Parquet/S3
```

Then your clients connect using Flight SQL.

### For your learning path

I'd think about it in this order:

```text
1. Parquet
      ↓
2. DuckDB
      ↓
3. Apache Arrow
      ↓
4. Apache Flight
      ↓
5. Flight SQL
```

And **don't add Flight SQL just because you're using Parquet**.

If you have:

```text
Python → DuckDB → Parquet
```

Flight SQL adds complexity without much benefit.

If you have:

```text
100 applications
       ↓
central analytics service
       ↓
DuckDB / Parquet
```

then Flight SQL becomes much more interesting.


## What if data is residing in the MySQL database, how can we use DuckDB and Flight SQL to make the query faster?

Yes, but **DuckDB + Flight SQL will not automatically make MySQL queries faster**. The key is to **move analytical workloads away from MySQL**.

For your banking scenario, I'd design it like this:

```text
                    OLTP
              ┌─────────────┐
              │    MySQL    │
              │ Core Banking│
              └──────┬──────┘
                     │
                CDC / ETL
                     │
                     ▼
             ┌───────────────┐
             │    Parquet    │
             │ Data Lake     │
             └───────┬───────┘
                     │
                     ▼
                ┌─────────┐
                │ DuckDB  │
                │  Query  │
                │ Engine  │
                └────┬────┘
                     │
                Flight SQL
                     │
                     ▼
              ┌────────────┐
              │ Analytics  │
              │ / Python   │
              │ / BI / ML  │
              └────────────┘
```

### Why this can be much faster

Suppose MySQL has:

```text
transactions
------------------------
2 billion rows
```

You ask:

```sql
SELECT
    branch_id,
    SUM(amount)
FROM transactions
WHERE transaction_date >= '2026-03-01'
  AND transaction_date < '2026-04-01'
GROUP BY branch_id;
```

If you execute this directly against MySQL:

```text
Application
     │
     ▼
   MySQL
     │
     ├── indexes
     ├── buffer pool
     ├── transaction processing
     └── aggregation
```

you're asking your **OLTP database** to perform an analytical workload.

---

## Better architecture

Use MySQL for transactions:

```text
                 MySQL
            Core Banking OLTP
                  │
                  │ CDC
                  ▼
             Data Lake
                  │
              Parquet
                  │
                  ▼
               DuckDB
                  │
             Flight SQL
                  │
                  ▼
          Analytics / ML / BI
```

Now the analytical query runs against Parquet/DuckDB:

```sql
SELECT
    branch_id,
    SUM(amount)
FROM transactions
WHERE transaction_date >= '2026-03-01'
  AND transaction_date < '2026-04-01'
GROUP BY branch_id;
```

DuckDB performs the analytical processing.

# What does Flight SQL actually improve?

This is important.

Flight SQL **doesn't make DuckDB's query execution faster**.

Instead:

```text
DuckDB
   │
   │ Arrow
   ▼
Flight SQL
   │
   │ high-performance transport
   ▼
Client
```

Flight SQL makes **remote access and transfer of analytical results efficient**.

So there are actually two performance improvements:

### 1. DuckDB

Improves **query processing** for analytical workloads.

```text
MySQL
  ↓
OLTP-oriented execution

DuckDB
  ↓
Columnar analytical execution
```

### 2. Arrow Flight SQL

Improves **data movement between the query engine and clients**.

```text
DuckDB
   ↓
Arrow RecordBatch
   ↓
Flight / gRPC
   ↓
Python / BI / ML
```

# But what if you need near-real-time data?

This is where your earlier **Debezium/CDC discussions** become relevant.

You can do:

```text
                 MySQL
                   │
                   │ CDC
                   ▼
              Parquet / Iceberg
                   │
                   ▼
                DuckDB
                   │
              Flight SQL
                   │
                   ▼
            Analytics / ML
```

For example:

```text
10:00:00  MySQL transaction
10:00:01  CDC captures change
10:00:02  Data lake updated
10:00:03  DuckDB can query it
```

The exact latency depends on the CDC/storage architecture.

# An even simpler architecture

If you don't need a permanent data lake yet, DuckDB can also query MySQL directly through its MySQL connectivity/extensions.

Conceptually:

```text
Client
   │
   ▼
Flight SQL Server
   │
   ▼
DuckDB
   │
   ▼
MySQL
```

But now DuckDB still has to pull data from MySQL:

```text
MySQL
   ↓
network transfer
   ↓
DuckDB
   ↓
aggregation
```

For **large analytical queries**, this may not give you the dramatic improvement you're expecting.

That's why this is generally better:

```text
MySQL
   │
   │ CDC
   ▼
Parquet
   │
   ▼
DuckDB
   │
   ▼
Flight SQL
   │
   ▼
Analytics
```

## The key architecture principle

Don't think:

> **"Let's put DuckDB and Flight SQL in front of MySQL to make MySQL faster."**

Think:

> **"Let's keep MySQL optimized for OLTP and move analytical processing to DuckDB + Parquet."**

For your **2-billion-transaction banking example**, I'd strongly favor:

```text
                    ┌──────────────────┐
                    │  Core Banking    │
                    │      MySQL       │
                    └────────┬─────────┘
                             │
                             │ CDC
                             ▼
                    ┌──────────────────┐
                    │ Parquet / Object │
                    │     Storage      │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │     DuckDB       │
                    │ Analytical Query │
                    │      Engine      │
                    └────────┬─────────┘
                             │
                       Flight SQL
                             │
                             ▼
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
           Python          BI Tool         ML
```

**MySQL = system of record**
**Parquet = analytical storage**
**DuckDB = analytical compute**
**Flight SQL = remote SQL + Arrow access**

That separation is what gives you the performance benefit—not Flight SQL alone.
