# 4. Why columnar format matters

Consider 100 million transactions.

You need:

```text
amount
```

only.

A row-oriented representation might conceptually look like:

```text
Transaction 1:
id, customer, date, amount, branch, channel...

Transaction 2:
id, customer, date, amount, branch, channel...

Transaction 3:
...
```

A columnar representation looks more like:

```text
transaction_id:  [1, 2, 3, 4, ...]
customer_id:     [101, 102, 103, ...]
date:            [...]
amount:          [500, 1200, 75, ...]
branch_id:       [...]
channel:         [...]
```

If the query needs only:

```text
amount
branch_id
transaction_date
```

the engine can focus on those columns.

This is particularly good for analytical workloads.

# 6. What about Polars?

Polars is another query/execution engine that works very naturally with Arrow-style columnar data.

For example:

```python
import polars as pl

result = (
    pl.scan_parquet("transactions.parquet")
      .filter(
          pl.col("transaction_date")
            .is_between("2026-01-01", "2026-01-31")
      )
      .group_by("branch_id")
      .agg(
          pl.col("amount").sum().alias("total_amount")
      )
      .collect()
)
```

Polars can optimize the query before executing it.

For example:

```text
Original query
      │
      ▼
Query optimizer
      │
      ├── Predicate pushdown
      ├── Projection pushdown
      ├── Lazy execution
      └── Parallel execution
      │
      ▼
Columnar execution
      │
      ▼
Result
```

DuckDB doesn't have to ingest those files into its own database.

---

## But DuckDB CAN store data itself

This is another important distinction.

You can create:

```text
banking.duckdb
```

and store tables inside that DuckDB database.

```sql
CREATE TABLE transactions AS
SELECT *
FROM read_parquet('transactions/*.parquet');
```

Now you have:

```text
                 DuckDB
              banking.duckdb
                    │
              ┌─────┴─────┐
              │           │
        transactions   customers
```

In this case, DuckDB **is acting as the database/storage engine**.

But that's different from:

```text
S3
 │
 └── Parquet
       │
       ▼
    DuckDB
     query
```

where Parquet remains outside DuckDB.

---

# For your Arrow Query Accelerator

I'd recommend the **second architecture**, especially if you're thinking about a scalable banking analytics product:

```text
              Oracle / MySQL
                    │
                    ▼
                 CDC/ETL
                    │
                    ▼
             Object Storage
             S3 / MinIO
                    │
                    ▼
              Parquet files
                    │
                    ▼
              ┌───────────┐
              │  DuckDB   │
              │           │
              │ Query     │
              │ Engine    │
              └─────┬─────┘
                    │
                    ▼
              Apache Arrow
                    │
                    ▼
              FastAPI / API
                    │
                    ▼

```

Here:

**S3/MinIO = storage**

**Parquet = file/data format**

**DuckDB = query engine**

**FastAPI = serving layer**

**React = visualization**

That's a very lightweight architecture compared with building a traditional data warehouse.

                 │

That's where the architecture becomes a true **lakehouse**.

## How to convert below into arrow table? 

SELECT
    branch_id,
    SUM(amount)
FROM read_parquet('/data/transactions/**/*.parquet')
WHERE transaction_date >= '2026-03-01'
  AND transaction_date < '2026-04-01'
GROUP BY branch_id;

Yes. There are **two different things** here:

1. DuckDB executes your SQL.
2. The **result of that SQL query can be returned directly as an Apache Arrow Table**.

You don't need to manually convert the SQL result through Pandas.

### Python example

```python
import duckdb

con = duckdb.connect()

arrow_table = con.execute("""
    SELECT
        branch_id,
        SUM(amount) AS total_amount
    FROM read_parquet('/data/transactions/**/*.parquet')
    WHERE transaction_date >= '2026-03-01'
      AND transaction_date < '2026-04-01'
    GROUP BY branch_id
""").fetch_arrow_table()

print(arrow_table)
```

Conceptually:

```text
                    Parquet
                       │
                       ▼
                  DuckDB
                       │
                  SQL Query
                       │
                       ▼
              Aggregated Result
                       │
                       │ fetch_arrow_table()
                       ▼
              ┌─────────────────┐
              │ Apache Arrow    │
              │     Table       │
              ├─────────────────┤
              │ branch_id       │
              │ total_amount    │
              ├─────────────────┤
              │ PHN001          │
              │ 42,500,000      │
              │ PHN002          │
              │ 31,200,000      │
              │ KOH001          │
              │ 18,700,000      │
              └────────┬────────┘
                       │
                       ▼
                 FastAPI/API
                       │
                       ▼
                  Dashboard
```

### What actually happens?

Your SQL:

```sql
SELECT
    branch_id,
    SUM(amount)
FROM read_parquet(...)
WHERE ...
GROUP BY branch_id;
```

is executed **inside DuckDB**.

DuckDB performs:

```text
Parquet
   ↓
Filter
   ↓
Read required columns
   ↓
SUM(amount)
   ↓
GROUP BY branch_id
   ↓
Small result
```

Then:

```python
.fetch_arrow_table()
```

asks DuckDB:

> "Give me the query result as an Apache Arrow Table."

So the important transition is:

```text
DuckDB execution
       │
       ▼
Query Result
       │
       ▼
Arrow Table
```

---

## You can then use the Arrow Table directly

For example, with PyArrow:

```python
import pyarrow as pa

print(type(arrow_table))

print(arrow_table.schema)
```

You would get something conceptually like:

```text
branch_id: string
total_amount: double
```

You can also convert it to Pandas **only if you need Pandas**:

```python
df = arrow_table.to_pandas()
```

So the pipeline becomes:

```text
                    Parquet
                       │
                       ▼
                    DuckDB
                       │
                       ▼
                 SQL execution
                       │
                       ▼
                  Arrow Table
                    /     \
                   /       \
                  ▼         ▼
             Pandas       Polars
                │            │
                ▼            ▼
               ML        Analytics
```

### And this is the key advantage

Instead of:

```text
Parquet
   ↓
DuckDB
   ↓
Pandas
   ↓
JSON
   ↓
API
```

you can potentially do:

```text
Parquet
   ↓
DuckDB
   ↓
Arrow
   ↓
API
```

or:

```text
Parquet
   ↓
DuckDB
   ↓
Arrow
   ↓
Polars
   ↓
ML
```

This is where **Arrow becomes the common interchange layer** between your analytical components.
